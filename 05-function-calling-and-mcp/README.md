# Function Calling и MCP

Конспект для AI Agents Developer. Базовые механики, которые лежат в основе всех современных агентов.

---

## Часть 1. Function Calling (Tool Use)

### Что это такое

Function calling — это способ дать LLM возможность вызывать твой код. Ты описываешь модели набор функций в виде JSON-схемы (имя, описание, параметры), и модель в ответ возвращает не обычный текст, а структурированный JSON: "я хочу вызвать функцию `get_weather` с параметрами `{city: "Istanbul"}`". Дальше твой runtime выполняет эту функцию, кладёт результат обратно в контекст, и модель продолжает рассуждение.

Это базовый примитив, на котором строятся все агенты: LLM как "мозг", оркеструющий вызовы реальных функций.

### Цикл работы

1. **User prompt + список tools** → модель
2. **Модель возвращает `tool_use` блок** с именем функции и аргументами
3. **Твой код выполняет функцию** (HTTP-запрос, SQL, что угодно)
4. **Возвращаешь результат** как `tool_result` обратно в messages
5. **Модель** либо вызывает следующий tool, либо отвечает финальным текстом

Сами функции живут у тебя в приложении — модель про них ничего не знает, кроме JSON-схемы.

### Пример на практике

Запрос пользователя: "Какая погода в Стамбуле?"

**Шаг 1 — твой код шлёт в API:**
```json
{
  "model": "claude-opus-4-7",
  "messages": [{"role": "user", "content": "Какая погода в Стамбуле?"}],
  "tools": [{"name": "get_weather", "input_schema": {...}}]
}
```

**Шаг 2 — модель возвращает:**
```json
{
  "content": [
    {"type": "tool_use", "id": "x", "name": "get_weather", "input": {"city": "Istanbul"}}
  ],
  "stop_reason": "tool_use"
}
```

**Шаг 3 — твой код выполняет реальный вызов к weather API**, получает `{"temp": 22, "condition": "sunny"}`.

**Шаг 4 — отправляешь продолжение истории:**
```json
{
  "messages": [
    {"role": "user", "content": "Какая погода в Стамбуле?"},
    {"role": "assistant", "content": [...предыдущий tool_use...]},
    {"role": "user", "content": [
      {"type": "tool_result", "tool_use_id": "x", "content": "{\"temp\": 22, ...}"}
    ]}
  ]
}
```

**Шаг 5 — модель формирует финальный ответ:** "В Стамбуле сейчас 22°C, солнечно."

Между шагами модель ничего не хранит внутри себя — она stateless. Полную историю надо передавать на каждом вызове.

### Function Calling vs Tool Calling — терминология

По сути это синонимы, путаница чисто историческая.

- **"Function calling"** — термин OpenAI с июня 2023. Исторически устоявшийся, все понимают.
- **"Tool calling" / "Tool use"** — современный термин. В ноябре 2023 OpenAI задеприкейтил `functions` в пользу `tools`. Anthropic с самого начала использовал термин `tool_use` в API.

Логика переименования: функция — это лишь один тип инструмента. Tool может быть не только функцией, но и встроенным web search, code interpreter, computer use.

В MCP официально используется термин **tools**.

### Что встроено в модель, а что вне её

**В модели обучены:**
- Понимание формата tools (JSON-схема в API)
- Решение, когда вызывать tool, а когда отвечать текстом
- Формирование корректных параметров
- Поведение в agent loop (мульти-шаг, остановка по завершении)

**Снаружи (runtime / твой код):**
- Реальное исполнение tools — HTTP-запросы, SQL, файлы
- Управление состоянием и историей сообщений
- Retry/fallback логика
- Оркестрация multi-step workflows

То есть модель **знает**, что и как вызвать. Реальный вызов делает твой код. Без runtime, замыкающего цикл, модель просто говорит "хочу вызвать tool" и останавливается.

## Часть 2. MCP (Model Context Protocol)

### Что это и зачем

MCP — открытый протокол от Anthropic (ноябрь 2024), который стандартизирует, как внешние системы предоставляют tools, ресурсы и промпты LLM-клиентам.

**Идея:** вместо того чтобы каждое приложение (Claude Desktop, Cursor, твой агент на Hetzner) реализовывало свою интеграцию с GitHub, Postgres, Slack — есть универсальный протокол клиент-сервер.

**Аналогия для бэкендера:**
- Function calling ≈ HTTP (механизм вызова)
- MCP ≈ OpenAPI/Swagger + service discovery (стандартизация интеграций)

Или ещё ближе: function calling = JDBC API, MCP = стандартный wire protocol, чтобы любая БД говорила с любым клиентом.

### Архитектура

**MCP server** — отдельный процесс, который экспортит набор tools. Например, `mcp-server-postgres` умеет выполнять SQL-запросы, `mcp-server-github` — работать с PR.

**MCP client** — встроен в LLM-приложение (Claude Desktop, IDE, твой агент). Держит соединение с серверами и проксирует их tools в function calling API модели.

**Транспорт** — JSON-RPC поверх stdio или HTTP+SSE/Streamable HTTP.

### Как это работает в связке с function calling

MCP сам по себе модель не вызывает. Он стандартизирует слой "откуда брать tools":

1. Агент стартует, MCP-клиент опрашивает серверы методом `tools/list`
2. Получает JSON-схемы tools, подсовывает в function calling вызов к API Claude
3. Когда модель решает вызвать tool — клиент маршрутизирует это в нужный MCP-сервер через `tools/call`
4. Сервер выполняет, возвращает результат

### Где физически живут MCP-серверы

**Локально (stdio transport)** — MCP-сервер запускается как дочерний процесс на той же машине. Общение через stdin/stdout, JSON-RPC построчно. Никакого сетевого слоя.

Пример конфига в Claude Desktop:
```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/docs"]
    }
  }
}
```

Когда Claude Desktop стартует — делает fork/exec, держит процесс живым, общается через пайпы.

**Удалённо (Streamable HTTP / SSE)** — MCP-сервер это HTTP-приложение, принимающее JSON-RPC поверх HTTP, со streaming через SSE. Деплоится где угодно:
- VPS как systemd unit или Docker контейнер
- Kubernetes как Deployment + Service
- Serverless (AWS Lambda + API Gateway, Cloud Run)
- Managed-облако вендора (Asana, GitHub, Notion хостят свои)

Авторизация — OAuth 2.1 или bearer-токены.

**Гибрид (часто встречается):** локально stdio-сервер, но внутри он прокси к удалённому API. Например `mcp-server-github` работает локально через stdio, но HTTP-запросы шлёт на api.github.com с твоим PAT. Удобно для безопасности — токены не уходят в чужой managed-сервис.

### Где живут tools (логика инструментов)

С точки зрения LLM "tool" — это:

1. **Декларация** (имя + JSON-схема + описание) — всегда внутри MCP-сервера
2. **Handler** (код, выполняющийся при `tools/call`) — всегда внутри MCP-сервера
3. **Эффект** (что реально происходит в мире) — может быть где угодно

Три паттерна реализации:

**Паттерн 1 — логика внутри сервера**
Сервер сам исполняет код. Пример: `mcp-server-filesystem` — внутри Node.js процесс с handler'ом, который дёргает `fs.readFile`. Tool `read_file` это буквально функция внутри процесса.

**Паттерн 2 — обёртка над внешним API**
Сервер переводит MCP tool calls в HTTP-запросы к чужому API. Пример: `mcp-server-github` — handler `create_issue` внутри делает fetch на `api.github.com`.

**Паттерн 3 — гибрид**
Большинство production-серверов комбинируют: часть tools исполняется локально, часть проксируется в API.

Это аналогия Spring `@RestController`: контроллер декларирует endpoint (= tool schema), у него есть метод-handler, внутри может дёргать БД, ходить в Kafka, бить в чужой REST. С точки зрения клиента — просто endpoint, под капотом — что угодно.

### Категории MCP-серверов

**1. Reference implementations от Anthropic**
Репо `modelcontextprotocol/servers` — эталонные реализации для filesystem, git, fetch, memory, time. MIT license, можно брать и использовать.

**2. Официальные серверы от вендоров продуктов**
GitHub, Atlassian (Jira+Confluence), Notion, Linear, Asana, Stripe, Cloudflare, Vercel, Sentry, Grafana, Supabase, Neon, AWS — все имеют свои официальные MCP-серверы. Часть локальные, часть managed remote.

**3. Community-серверы**
Сотни в каталогах: `mcp.so`, `glama.ai/mcp`, `smithery.ai`. Качество разное, гигиена: смотри звёзды, последние коммиты, кто автор. Особенно если требует API-токены — это канал утечки credentials.

**4. Internal/самописные**
Пишут сами разработчики агентов:
- Доступ к внутренним API
- Бизнес-логика поверх стандартных tools (вместо raw `query` → `get_customer_ltv(id)` с зашитыми join'ами)
- Compliance/security (логирование в SIEM, SSO, маскирование PII)
- Композитные tools, ходящие в 3-4 системы

### Типичный стек продакшен-агента

- 2-3 публичных серверов от вендоров (Slack, GitHub, Linear)
- 1-2 reference-серверов (filesystem, fetch)
- N внутренних серверов для своих API

Писать MCP-сервер с нуля имеет смысл, когда tool обслуживает то, чего ни у кого нет публично.

## Ключевые выводы для собеседования / работы

1. **Function calling — это нативная способность модели**, не prompt-trick. Современные LLM специально обучаются на структурированном tool use.

2. **Модель решает, что вызывать. Runtime исполняет.** Без runtime, замыкающего цикл, агент не работает.

3. **MCP стандартизирует слой tools.** Тот же tool работает в Claude Desktop, IDE, твоём агенте.

4. **Транспорты MCP:** stdio (локально, дочерний процесс) и HTTP/SSE (удалённо).

5. **Внутри MCP-сервера живут tool declarations + handlers.** Сам эффект может быть где угодно (локально, в чужом API, в БД).

6. **OAuth 2.1 для аутентификации remote MCP-серверов.**

7. **Stateless модель + stateful runtime.** Историю сообщений всегда подавай заново. Внутри одного inference call модель ничего не помнит "между запросами".
