# RAG (Retrieval-Augmented Generation) — конспект

## Что такое RAG и зачем он нужен

У LLM есть три фундаментальных ограничения:

1. **Знания заморожены на дате обучения.** Модель не знает, что произошло после её cutoff.
2. **Нет доступа к приватным данным.** Модель не видела твою кодовую базу, внутреннюю Confluence, переписку в Slack, твою БД клиентов.
3. **Галлюцинации.** Если модель не знает ответа, она часто его выдумывает — особенно на специфичных доменных вопросах.

RAG решает все три проблемы одним приёмом: **перед тем как спросить модель, найди в своём корпусе релевантные куски и подсунь их в контекст вместе с вопросом**. Модель отвечает не из памяти, а на основе того, что ты ей предоставил.

По сути это превращение LLM из «всезнающего оракула» в «умного аналитика с доступом к твоей базе знаний».

### Когда RAG нужен

- Корпоративный поиск / Q&A по документации.
- Customer support боты на базе FAQ и тикетов.
- Чат с документами (PDF, контракты, медкарты).
- Дев-ассистенты по конкретной кодовой базе.
- Внутренние знания организации (политики, регламенты).
- Персональный second brain (заметки, статьи, переписки).
- Регулятивные/комплаенс задачи.
- Свежая информация (новости, цены, документация быстро меняющихся библиотек).

### Когда RAG НЕ нужен

- Общие знания, которые модель и так знает («объясни квиксорт», «как работает OAuth»).
- Творческие задачи (слоганы, имена, истории).
- Чистые reasoning-задачи (математика, дебаг, код-ревью).
- Когда данные помещаются прямо в контекст (1 PDF на 50 страниц — просто положи целиком).
- Сложная аналитика по структурированным данным — это SQL/text-to-SQL, не векторный поиск.
- Real-time действия — это function calling, не RAG.

### Эвристика принятия решения

Перед тем как тянуть RAG, задай три вопроса:

1. Зависит ли качество ответа от данных, которых нет в модели? Если нет → RAG не нужен.
2. Эти данные помещаются в контекстное окно одного запроса? Если да → просто клади всё в промпт.
3. Это поиск/вспоминание или это рассуждение/вычисление/действие? Если второе → RAG не тот инструмент.

Только если ответы «да, не помещаются, это поиск» — берёшь RAG.

## Document loading & parsing

Это процесс затаскивания исходных документов в систему и превращения их в чистый текст.

**Источники:** PDF, Word, HTML, Markdown, Confluence, S3, БД, тикеты в Jira, исходники в Git.

**Подводные камни по форматам:**
- В PDF — многоколоночная вёрстка и таблицы.
- В HTML — выкинуть навигацию и рекламу.
- В сканах — прогнать OCR.

**Популярные инструменты:**
- **LangChain DocumentLoaders**
- **LlamaIndex Readers**
- **Unstructured.io** — хорошо справляется со сложными PDF
- **Apache Tika** — для JVM-экосистемы
- **PyPDF / pdfplumber**
- **BeautifulSoup** — для HTML

На выходе обычно получаешь объект вида `Document(text, metadata)`, где в метаданные кладут источник, дату, автора, страницу — потом это пригодится для фильтрации при поиске.

## Chunking strategies

LLM имеют ограниченный контекст, а векторный поиск работает лучше на коротких смысловых кусках, чем на простынях. Поэтому документы режут на чанки.

### Fixed-size (фиксированный размер)

Режешь по N токенов или символов, обычно с overlap (например, 512 токенов + 50 токенов перекрытия).

**Плюсы:** простой, быстрый, дешёвый.
**Минусы:** рубит по живому — предложение, таблица или код могут разорваться посередине.

### Recursive

Рекурсивно делит по иерархии разделителей: сначала пытается резать по `\n\n` (параграфы), если кусок всё ещё слишком большой — по `\n`, потом по точкам, потом по пробелам.

Это дефолт в `RecursiveCharacterTextSplitter` у LangChain и в большинстве продакшен-сетапов. **Хороший баланс между качеством и стоимостью.**

### Semantic

Самый умный и самый дорогой. Считаешь эмбеддинги для каждого предложения, а потом группируешь соседние предложения, у которых cosine similarity выше порога. Граница чанка ставится там, где смысл резко меняется.

**Плюсы:** куски тематически целостны.
**Минусы:** за каждый документ платишь эмбеддингами ещё на этапе индексации.

### Структурно-зависимый чанкинг

- Для Markdown — режут по заголовкам (`#`, `##`).
- Для кода — по AST (функция/класс целиком).
- Для HTML — по тегам.

### Parent-child / small-to-big

Индексируешь маленькие чанки (точнее ретривал), а в контекст модели подкладываешь родительский большой чанк (больше контекста для ответа).

### Практический старт

Recursive с размером 500–1000 токенов и overlap 10–20%. Семантический включаешь, когда видишь, что качество поиска проседает из-за рубленых смыслов.

## Embeddings generation через API

### Что такое эмбеддинг

Эмбеддинг — это плотный вектор фиксированной длины (например, 1536 или 3072 чисел), который отражает «смысл» текста в многомерном пространстве.

**Ключевое свойство:** семантически близкие тексты дают близкие векторы. Близость измеряют косинусным расстоянием (или dot product / евклидовым).

В RAG ты эмбеддишь дважды:
1. На этапе индексации — все чанки документов.
2. На этапе запроса — эмбеддишь вопрос пользователя.

Потом ищешь top-K ближайших чанков в векторной БД.

### Провайдеры

- **OpenAI** — `text-embedding-3-small` (1536 dim, ~$0.02/1M токенов) и `text-embedding-3-large` (3072 dim, ~$0.13/1M). Поддерживают параметр `dimensions` — можно урезать вектор для экономии места.
- **Voyage AI** — `voyage-3`, `voyage-3-large`, `voyage-code-3`. Anthropic официально рекомендует.
- **Cohere** — `embed-v4.0`, мультиязычные, поддерживают разделение query vs document эмбеддингов (`input_type`).
- **Google** — `gemini-embedding-001` / `text-embedding-004`.
- **Mistral, Jina, BGE** — для опенсорс/локальных вариантов.

### Практические соображения

**Батчинг.** API принимают массив текстов за один запрос (обычно до 2048 элементов или ~8K токенов на элемент). Группируй пачками по 100–500.

**Стоимость.** Индексация большого корпуса — разовая, но дорогая операция. Миллион чанков по 500 токенов на `text-embedding-3-small` — около $10. На `voyage-3-large` уже $60.

**Консистентность модели.** Менять модель эмбеддингов на лету нельзя — векторы от разных моделей несравнимы. Сменил модель → переиндексируй весь корпус.

**Размерность vs хранение.** 3072-мерный вектор в float32 — это 12 KB на чанк. Миллион чанков — 12 GB только под векторы. Либо урезай dimensions, либо используй квантизацию в БД (int8, binary).

**Асимметричные эмбеддинги.** Cohere и Voyage различают тип входа: `input_type=query` для вопросов и `input_type=document` для индексации. У OpenAI этого нет.

**Кэширование.** Если один и тот же запрос приходит часто — кэшируй эмбеддинг по хешу текста. Redis + TTL подходит.

В Java-стеке для эмбеддингов берут **Spring AI** (`EmbeddingModel` абстракция) или **LangChain4j** — обе библиотеки прячут API-вызовы и батчинг за единым интерфейсом.

## Как модель понимает близость по смыслу

Самый частый вопрос: как алгоритмически модель понимает, что «налить кофе» и «выпить эспрессо» близки по смыслу, хотя у них нет ни одного общего слова?

### Базовая идея: смысл = позиция в пространстве

Представь, что каждое слово — это точка в пространстве. Не в 2D или 3D, а в 768-мерном или 1536-мерном. Звучит страшно, но математически это просто массив из N чисел: `[0.23, -0.41, 0.88, ...]`.

Ключевая интуиция: **если научиться расставлять слова в этом пространстве так, что близкие по смыслу слова оказываются рядом — то «близость по смыслу» превращается в «близость в пространстве», которую можно посчитать формулой**.

### Distributional hypothesis — фундамент всего

В 1950-х лингвист Зеллиг Харрис сформулировал гипотезу: **«слова, которые встречаются в похожих контекстах, имеют похожий смысл»**. Джон Фёрс позже афористичнее: *«You shall know a word by the company it keeps»*.

Посмотри сам:
- «налить **кофе** в чашку», «выпить **кофе** утром», «заказать **кофе** в баре»
- «налить **эспрессо** в чашку», «выпить **эспрессо** утром», «заказать **эспрессо** в баре»

Слова «кофе» и «эспрессо» окружены практически идентичными словами в миллиардах текстов. А «кофе» и «трактор» — нет. Это и есть сигнал, который ловит модель.

То есть никто вручную не сказал модели «кофе ≈ эспрессо». Она вывела это из статистики совместной встречаемости.

### Word2Vec — на нём понятнее всего

Алгоритм 2013 года. Уже устаревший по сравнению с трансформерами, но идея — основа всего, что есть сейчас.

**Setup.** Берёшь огромный корпус текстов (Википедия, Common Crawl — триллионы слов). Каждому уникальному слову в словаре присваиваешь случайный вектор из, скажем, 300 чисел. На старте это полный мусор — никакого смысла там нет.

**Задача обучения (skip-gram).** Берёшь центральное слово и пытаешься предсказать его соседей в окне ±5 слов.

Пример: «утром я налил себе кофе и пошёл работать»
Центральное слово: «кофе»
Соседи: «налил», «себе», «и», «пошёл»

Нейросеть получает на вход вектор слова «кофе» и должна выдать высокую вероятность для векторов соседей и низкую — для случайных слов из словаря.

**Магия обучения.** Если предсказание плохое — алгоритм backprop корректирует векторы. Чуть-чуть двигает вектор «кофе» в сторону векторов «налил» и «утром», и чуть-чуть отодвигает от «трактор». И так миллиарды раз на миллиардах примеров.

**Что происходит со словами «кофе» и «эспрессо»?** Оба слова в корпусе встречаются рядом с «налил», «выпил», «горячий», «чашка», «утром», «бариста». Значит, на каждом шаге оба вектора корректируются в сторону одних и тех же соседей. После миллиардов шагов они неизбежно оказываются в одной области пространства — не потому, что их кто-то туда поставил, а потому что их одинаково «тянуло» к одним и тем же якорям.

Это эмерджентное свойство: смысл не запрограммирован, он *выпадает в осадок* из статистики.

### Как меряется близость — косинусное сходство

Самая популярная формула:

```
cos(θ) = (a · b) / (||a|| · ||b||)
```

В числителе — скалярное произведение (сумма попарных произведений координат), в знаменателе — произведение длин. Геометрически — это косинус угла между векторами.

- `1.0` → векторы смотрят в одну сторону (синонимы)
- `0.0` → перпендикулярны (не связаны)
- `-1.0` → противоположны (антонимы)

**На пальцах в 2D.** Допустим:
- «кофе» = `[0.9, 0.4]`
- «эспрессо» = `[0.85, 0.45]`
- «трактор» = `[-0.3, 0.7]`

Угол между «кофе» и «эспрессо» крошечный → косинус ≈ 0.99. Угол между «кофе» и «трактор» большой → косинус ≈ -0.05.

Почему **косинусное**, а не евклидово расстояние? Потому что важно *направление*, а не длина вектора. Длинный текст и короткий могут говорить об одном — у них совпадёт направление, но не модуль.

### Знаменитая иллюстрация: арифметика смысла

В Word2Vec обнаружили, что в обученном пространстве работает арифметика:

```
vec("король") - vec("мужчина") + vec("женщина") ≈ vec("королева")
vec("Париж") - vec("Франция") + vec("Италия") ≈ vec("Рим")
```

Это значит, что в пространстве выделились *направления*, кодирующие осмысленные оси: «гендер», «столица страны», «время глагола». Никто их не задавал — они эмерджентно выделились из статистики.

### От слов к фразам: современные модели

Word2Vec — это про отдельные слова, и у него фатальная проблема: одно слово = один вектор. Слово «коса» (волосы / инструмент / песчаная коса) получает один усреднённый вектор, и это плохо.

Современные эмбеддинг-модели (BERT, OpenAI `text-embedding-3`, Voyage, Cohere) построены на **трансформерах**. Ключевое отличие — **контекстуальные эмбеддинги**: вектор слова зависит от окружения в конкретном предложении.

Грубая схема:
1. Текст бьётся на токены.
2. Каждый токен получает базовый вектор + позиционный.
3. **Attention** — каждый токен «смотрит» на все остальные токены в предложении и обновляет свой вектор с учётом контекста. «Коса» в «заплела косу» получит совсем другой вектор, чем «коса» в «вышел на косу с удочкой».
4. После N слоёв attention собираешь финальный вектор для всего предложения — обычно усреднением или взятием специального `[CLS]` токена.

Обучают это уже не на skip-gram, а на других задачах — masked language modeling (предскажи закрытое слово), contrastive learning (две перефразированные версии одного предложения должны дать близкие векторы, разные — далёкие).

Фундаментальный принцип тот же: **смысл = позиция в пространстве, расстояние = математическая близость векторов, обучение = подгонка позиций по статистике из триллионов токенов**.

### Почему это работает — короткий ответ

Потому что язык избыточен. Один и тот же смысл выражается тысячами разных формулировок, но всегда в похожих контекстах. Достаточно дать модели достаточно большой корпус, и геометрия пространства сама собой выстраивается так, чтобы отражать семантику.

Эмбеддинги — это, по сути, *сжатая статистика всего интернета*, переложенная на координаты. «Кофе» и «эспрессо» близки потому, что в человеческих текстах они *ведут себя* одинаково.

## Vector store

Специализированные хранилища, заточенные под хранение и поиск по векторам-эмбеддингам.

### Зачем нужен отдельный класс БД

Обычная реляционка не умеет отвечать на вопрос «найди мне 10 векторов, ближайших к вот этому по косинусному расстоянию». При миллионе векторов полный скан занимает секунды.

Vector store решает две задачи:
1. **Хранение** векторов вместе с исходным текстом и метаданными.
2. **Approximate Nearest Neighbor (ANN) поиск** — индексы, которые находят почти-ближайших соседей за O(log N) с потерей точности в 1–5%.

Под капотом — алгоритмы:
- **HNSW** (Hierarchical Navigable Small World) — сейчас де-факто стандарт.
- **IVF** (Inverted File Index).
- **PQ** (Product Quantization для сжатия).

HNSW строит многоуровневый граф соседства, по которому жадно спускаешься к ближайшим точкам.

### Основные опции

**pgvector** — расширение для PostgreSQL. Главный плюс: остаёшься в Postgres со всеми его транзакциями, бэкапами, ACL, джойнами. Поддерживает HNSW и IVFFlat индексы, метрики L2 / cosine / inner product. Хороший дефолт до сотен миллионов векторов.

```sql
CREATE EXTENSION vector;
CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  doc_id text,
  content text,
  embedding vector(1536),
  metadata jsonb
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

SELECT content, 1 - (embedding <=> $1) AS similarity
FROM chunks
WHERE metadata->>'source' = 'docs'
ORDER BY embedding <=> $1
LIMIT 10;
```

`<=>` — оператор косинусного расстояния.

**Pinecone** — managed-only облачный сервис. Платишь за pod-часы или serverless. Плюсы: ничего не админить, авто-скейлинг, namespaces для мультитенантности. Минусы: vendor lock-in, дорого на больших объёмах.

**Chroma** — опенсорсная, изначально embedded (как SQLite). Удобна для прототипов, локальной разработки, небольших проектов.

**Qdrant** — Rust-овый опенсорс, отличная производительность, хорошее API, есть managed cloud и self-hosted.

**Weaviate** — опенсорс на Go, умеет встроенную векторизацию, GraphQL API, гибридный поиск из коробки.

**Milvus** — опенсорс, заточен под огромные масштабы (миллиарды векторов), сложнее в эксплуатации.

**Elasticsearch / OpenSearch** — есть HNSW и dense_vector. Имеет смысл, если уже сидишь на ELK.

**Redis** — RediSearch с векторным индексом. Быстрый, но in-memory, дорого по RAM.

### Что важно при выборе

**Масштаб.** До ~10M векторов — pgvector справляется отлично. 10M–100M — pgvector с тюнингом или Qdrant/Pinecone. Больше — Milvus, Vespa, Pinecone.

**Filtered search.** Самая частая боль в продакшене: «найди ближайшие чанки, но только из документов пользователя X, опубликованных после такой-то даты». Две стратегии — pre-filtering (фильтр потом ANN на подмножестве) и post-filtering (top-K потом фильтр). Pre-filtering точнее.

**Гибридный поиск.** Часто чистый векторный поиск проигрывает связке «векторный + BM25». Weaviate, Qdrant, Elasticsearch, OpenSearch поддерживают это нативно.

**Persistence и операции.** В Postgres решено десятилетиями. В нишевых БД — приходится разбираться.

**Транзакции и консистентность.** Если эмбеддинги логически связаны с другими бизнес-данными — pgvector выигрывает, потому что всё в одной транзакции.

## Similarity search

Базовая операция RAG: «дай мне K чанков, наиболее похожих на запрос». Под капотом — поиск ближайших соседей в векторном пространстве.

### Как работает

1. Все чанки документов заранее эмбеддированы и лежат в векторной БД.
2. Приходит запрос → эмбеддишь его той же моделью.
3. Считаешь расстояние от вектора запроса до каждого вектора в БД.
4. Возвращаешь top-K с наименьшим расстоянием.

### Метрики расстояния

**Cosine similarity** — косинус угла между векторами. Чувствителен к направлению, не к длине. Самая популярная метрика для текстовых эмбеддингов.

**Dot product (скалярное произведение)** — то же, что cosine, но без нормировки. Чувствителен и к направлению, и к длине. Быстрее cosine. OpenAI эмбеддинги уже нормализованы, поэтому dot product = cosine.

**Euclidean (L2) distance** — обычное расстояние в пространстве. Реже используется для текстов, чаще для изображений.

### ANN — почему не точный поиск

Точный поиск ближайших соседей (kNN) — это O(N): надо посчитать расстояние от запроса до каждого из миллиона векторов. Это секунды на запрос — неприемлемо.

ANN жертвует 1–5% точности ради скорости O(log N).

### Где similarity search ломается

Чистый векторный поиск отлично ловит семантику, но плохо работает в нескольких случаях:

- **Точные термины и имена собственные.** «Lambda SnapStart» — модель эмбеддингов знает Lambda и snapstart как «что-то AWS-ное», но в корпусе её могут окружать вектора всех Lambda-фич.
- **Идентификаторы, номера, версии.** «Spring Boot 3.2.4» — модель не различит 3.2.4 и 3.2.5.
- **Аббревиатуры и сленг.** Внутренний жаргон компании, кодовые названия проектов.
- **Negation.** «Документы НЕ про deprecation» — эмбеддинг считает «не про deprecation» примерно тем же, что «про deprecation».

Решение всех этих проблем — hybrid search.

## Hybrid search

**Комбинируй векторный поиск с классическим keyword-поиском**, чтобы получить лучшее из обоих миров. Сейчас это де-факто стандарт в production-RAG.

### Keyword-часть — BM25

Эволюция TF-IDF, фундамент Elasticsearch, OpenSearch, Lucene. Интуиция:
- Документ релевантен, если в нём часто встречается термин из запроса.
- Термин редко встречается в корпусе (значит, он информативный).
- Документ не слишком длинный.

BM25 идеально ловит точные совпадения по словам, имена собственные, идентификаторы, версии. Но слеп к семантике: «купить кофе» и «приобрести эспрессо» для BM25 — два разных запроса без общих слов.

### Векторный + BM25

Векторный поиск ловит семантику, BM25 ловит лексику. Вместе — мощно.

### Как комбинировать результаты

У тебя на выходе два ранжированных списка от двух разных методов.

#### Reciprocal Rank Fusion (RRF)

Самый популярный метод. Для каждого документа в каждом списке:

```
score(d) = Σ 1 / (k + rank_i(d))
```

где `rank_i` — позиция документа в i-том списке, `k` — константа (обычно 60).

RRF элегантен тем, что не требует калибровки. Разные методы (BM25, cosine) выдают scores в разных шкалах — у BM25 это может быть 15.3, у cosine — 0.87. Складывать их напрямую нельзя. RRF использует только ранги.

#### Weighted linear combination

Альтернатива: нормализуешь scores в [0,1] и считаешь `α * vector_score + (1-α) * bm25_score`. Гибче, но требует тюнинга.

### Пример где hybrid выигрывает

Запрос: «как откатить deployment v2.3.1 в нашем k8s кластере».

- **Pure vector** найдёт документы про rollback в Kubernetes в принципе, потеряв конкретику версии.
- **Pure BM25** найдёт документы со словом «v2.3.1» или «rollback», но может пропустить релевантную статью где описано то же самое словами «откат релиза».
- **Hybrid** вытащит и то, и другое — статью про rollback в k8s (по семантике) и changelog для v2.3.1 (по точному совпадению).

### Поддержка

- **Нативно:** Elasticsearch, OpenSearch, Weaviate, Qdrant, Pinecone.
- **В pgvector** комбинируешь сам через `tsvector` (полнотекстовый индекс Postgres) + векторный поиск, два запроса, RRF в коде приложения.

```sql
WITH vector_search AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
  FROM chunks ORDER BY embedding <=> $1 LIMIT 50
),
keyword_search AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank(tsv, query) DESC) AS rank
  FROM chunks, plainto_tsquery($2) query
  WHERE tsv @@ query LIMIT 50
)
SELECT id, SUM(1.0 / (60 + rank)) AS score
FROM (SELECT * FROM vector_search UNION ALL SELECT * FROM keyword_search) combined
GROUP BY id ORDER BY score DESC LIMIT 10;
```

### Эмпирика

На большинстве production бенчмарков hybrid search даёт **+10–30% к recall@10** по сравнению с pure vector. На некоторых доменах (юридические, технические тексты с терминами и кодами) — до **+50%**.

## Re-ranking

Это второй этап после initial retrieval. Идея: **первый этап достаёт много кандидатов широкой сетью, второй этап точечно их переранжирует более дорогой и точной моделью**.

### Зачем два этапа

Векторный поиск через эмбеддинги — это **bi-encoder** представление: запрос и документ эмбеддятся независимо, потом считается расстояние. Это быстро (можно проиндексировать заранее), но информация о взаимодействии запроса и документа теряется.

**Cross-encoder** — более точная альтернатива. Модель получает пару (запрос, документ) одновременно и выдаёт score релевантности. Под капотом — обычный transformer с attention между токенами запроса и токенами документа.

Цена — скорость. Bi-encoder можешь применить к миллиону документов заранее. Cross-encoder надо применять в момент запроса для каждой пары — это нереально на миллионе документов.

### Пайплайн

1. **Bi-encoder** (быстрый, неточный): достань top-50 кандидатов из миллиона.
2. **Cross-encoder** (медленный, точный): переранжируй эти 50 → топ-5.

Это даёт лучшее из двух миров: скорость на масштабе и точность на финальной выдаче.

### Какие модели используют

- **Cohere Rerank** (`rerank-v3.5`, `rerank-multilingual`) — managed API, индустриальный лидер. Качество отличное, мультиязычно.
- **Voyage rerank** — конкурент Cohere, заметно дешевле.
- **BGE Reranker** (BAAI) — open-source, можно хостить локально на GPU. Хорошее качество, бесплатно. Версии под разные размеры (base, large) и языки.
- **Jina Reranker** — открытый, ещё один достойный вариант.

### Метрика и оверхед

Типично reranker даёт **+5–15% к recall@5** и заметно лучшее качество в топе. Латентность — десятки-сотни миллисекунд на батч из 50 документов через API. На GPU локально — единицы миллисекунд.

### Продвинутые re-ranking техники

**LLM-as-a-judge re-ranking.** Берёшь GPT-4 или Claude, скармливаешь запрос и top-N кандидатов, просишь отранжировать. Качество выше любых специализированных rerankers, но дорого и медленно.

**Listwise vs pointwise.** Pointwise reranker оценивает каждую пару независимо. Listwise — видит весь список и ранжирует целиком, что точнее, но сложнее.

### Родственные подходы

**Maximal Marginal Relevance (MMR).** Балансирует «релевантность к запросу» против «разнообразия среди выбранных». Полезно, когда корпус с дубликатами или вариациями одного контента.

**HyDE (Hypothetical Document Embeddings).** Pre-retrieval техника. Вместо эмбеддинга запроса просишь LLM сгенерировать гипотетический ответ на запрос, и эмбеддишь этот ответ. Идея: гипотетический ответ ближе по смыслу к настоящему ответу в корпусе, чем сам вопрос.

## Evaluation качества retrieval

Самая недооценённая часть RAG-инженерии. Большинство команд строит RAG, отвечает «ну вроде нормально работает», и ловит галлюцинации в проде. Без evaluation ты летишь вслепую.

Разделим на две задачи: оценка retrieval (что нашли) и оценка generation (что ответили).

### Метрики retrieval

Эти метрики приходят из информационного поиска (IR), им десятилетия.

#### Recall@K

Из всех релевантных документов сколько попало в top-K?

Пример: для запроса релевантны 4 документа, top-10 содержит 3 из них → recall@10 = 0.75.

**Главная метрика**, когда тебе важно не пропустить ничего важного.

#### Precision@K

Из top-K сколько релевантных?

Пример: top-10 содержит 3 релевантных → precision@10 = 0.30.

Полезна, когда LLM имеет маленький контекст и нельзя кормить мусором.

#### Mean Reciprocal Rank (MRR)

Учитывает позицию первого релевантного документа. MRR = 1/rank первого релевантного. Усредняешь по всем запросам в датасете.

Важна, когда пользователю надо найти один правильный ответ быстро.

#### Normalized Discounted Cumulative Gain (nDCG@K)

Самая богатая метрика. Учитывает и позицию, и градации релевантности (не бинарно, а 0/1/2/3).

Стандарт в IR-бенчмарках (BEIR, MTEB).

#### Hit Rate@K

Самая простая: попал ли хоть один релевантный документ в top-K? Бинарно, по запросам усредняется.

### Как получить ground truth

Главная боль — нужен датасет с разметкой «для запроса X релевантны документы [A, B, C]».

**Ручная разметка** — самый точный, самый дорогой. Берёшь 100–500 запросов, эксперты размечают релевантность.

**Synthetic data generation.** Просишь LLM сгенерировать вопросы по каждому чанку: «вот документ, придумай 3 вопроса, на которые он отвечает». Дёшево и быстро, но качество ниже ручного.

**User feedback.** В продакшене собираешь сигналы — thumbs up/down, какие источники пользователь раскрыл, что зарепортил как плохое.

**Public benchmarks.** BEIR (18 датасетов на разные домены), MTEB (Massive Text Embedding Benchmark) — публичные бенчмарки.

### Метрики generation (RAGAS)

Кроме retrieval нужно оценивать сам ответ. Здесь индустрия пришла к LLM-as-a-judge: используешь сильную LLM (GPT-4, Claude) как оценщика.

Самый известный framework — **RAGAS**. Стандартные метрики:

**Faithfulness.** Соответствует ли ответ извлечённому контексту? Низкая faithfulness — модель галлюцинирует поверх контекста.

**Answer Relevance.** Отвечает ли модель на заданный вопрос, или уходит в сторону?

**Context Precision.** В извлечённом контексте сколько действительно нужного? Если из 10 чанков для ответа нужны были 2 — остальные 8 — мусор.

**Context Recall.** Содержит ли извлечённый контекст всё нужное для полного ответа?

**Answer Correctness.** Совпадает ли ответ с ground truth? Семантически, не лексически.

Эти метрики автоматически считаются на тестовом датасете, выдают числа от 0 до 1. Можно использовать в CI как unit-тесты для RAG.

### Альтернативные фреймворки

- **TruLens** — конкурент RAGAS.
- **LangSmith** (от LangChain) — managed observability + evaluation.
- **Langfuse** — open-source observability, можно self-host.
- **OpenLLMetry** — на основе OpenTelemetry.
- **DeepEval** — фреймворк с pytest-like синтаксисом.

### Практический процесс

1. Соберёшь evaluation dataset (50–500 запросов с эталонными ответами).
2. Настроишь RAGAS или аналог как часть CI pipeline.
3. Замеряешь baseline: текущий RAG даёт recall@10 = 0.72, faithfulness = 0.81.
4. Пробуешь изменения: новая chunking стратегия → recall@10 = 0.78, faithfulness = 0.85. Принимаешь.
5. Пробуешь reranker → faithfulness = 0.91. Принимаешь.
6. Пробуешь сменить эмбеддинг-модель → context precision просел. Откатываешь.

Без этого процесса каждое изменение — это «надеюсь, не сломал».

### Reality check

- Сбор хорошего eval dataset — 30–50% работы по запуску production RAG.
- LLM-as-a-judge сам по себе шумный — нужны несколько прогонов, осреднение, иногда два разных судьи.
- Метрики коррелируют между собой, и улучшение одной может убить другую.
- Бенчмарки в академических бумагах часто не переносятся на твой домен — нужно мерить на своих данных.

## Сводная картина RAG-пайплайна

```
[Документы] → loading/parsing → chunking → embeddings → vector store
                                                              ↓
[Запрос] → embedding → hybrid search (vector + BM25) → top-50
                                                              ↓
                                                      re-ranking
                                                              ↓
                                                       top-5 chunks
                                                              ↓
                                            LLM + контекст → ответ
                                                              ↓
                                                      evaluation (RAGAS)
```

Каждый этап — отдельный рычаг качества. Чем глубже тюнинг каждого этапа, тем выше итоговое качество системы.
